# l2h Query Language — Семантика (RU)

Status: **заморожена** (v1.1).  
Документ — семантический эталон LINQ-подобного языка над хешами. Наблюдаемое поведение соответствует текущему интерпретатору `QueryPlan`, если раздел не помечает известное ограничение.

**Languages:** [English](l2h-semantics.md) · **Русский**

**Правила правок:** изменение поведения — с повышением версии (v1.2+ для совместимых расширений; v2.0 для breaking). Редакционные уточнения без смены поведения — без bump. Реализация: `src/l2h/plan.zig`, `expr.zig`, `value.zig`, `lower.zig`, `interpret.zig`, `diag.zig`.

---

## 1. Назначение

l2h вычисляет **query-выражения**, которые:

1. Связывают **range-переменные** с источниками (`string`, `file`, `dir`, `hash`).
2. Преобразуют **последовательности окружений** LINQ-подобными выражениями.
3. Читают **ленивые (demand-driven) вычисляемые свойства** (size, digests, …).
4. Либо **печатают** терминальную проекцию, либо передают последовательность через **`into`**.

Стоимость хеш-алгоритмов доминирует; интерпретатор можно делать ясным и тестируемым, без микрооптимизаций.

## 2. Модель значений

### 2.1 Виды значений

| Вид | Смысл |
|-----|--------|
| `String` | Текст (в т.ч. digest и пути как строки) |
| `File` | Обычный файл по пути |
| `Dir` | Каталог по пути (источник перечисления, не «вечная» строка результата) |
| `Hash` | Источник restore: строка digest (+ алгоритм через property / select) |
| `Int` | Целое (размеры, числовые литералы) |
| `Bool` | Результат предиката |
| `Record` | Анонимный объект / продукт `let` / join |
| `Seq(T)` | Ленивая последовательность значений или окружений |

### 2.2 Окружение

**Окружение** (`Env`) — конечный map: имя range-переменной → `Value`.

Выражение запроса принимает последовательность окружений и выдаёт новую (или после `select`/`group` — последовательность проекций).

### 2.3 Источники (`from`)

| Объявление | Последовательность |
|------------|-------------------|
| `from string x in E` | Singleton: один `String` из `E` |
| `from file x in E` | Singleton: один `File` по пути `E` (ошибка, если нет / не файл) |
| `from dir x in E` | Singleton: один `Dir` по пути `E` (ошибка, если нет / не каталог) |
| `from hash x in E` | Singleton: один `Hash` с digest из `E` |

**Содержимое каталога не подставляется неявно в переменную `from dir`.** Файлы — только явным вторым `from` (SelectMany):

```text
from dir d in '/tmp'
from file f in d
where f.size > 0
select f.md5;
```

`from file f in d`: для текущего `Dir` в `d` — по одному окружению на каждый **непосредственный дочерний regular file** (§2.4), `f` → `File` (`d` остаётся в scope, если не затенён).

**Правило типа:** выражение после `in` в этой форме должно давать **`Dir`**. Голый path-string **не** принимается — сначала `from dir d in '/tmp'`, затем `from file f in d`. Неверный runtime-вид → ошибка.

Дополнительные `from` в body — всегда **SelectMany**.

### 2.4 Обход каталога (v1.1)

- Только **плоский** список непосредственных детей.
- Только **regular files**; **все symlink пропускаются** (на файл или каталог), подкаталоги тоже.
- **Без рекурсии** в v1.1 (замороженный non-goal). Рекурсию в будущей версии можно дать фильтрами и синтетическими свойствами, а не встроенным recursive `from dir`.

Порядок детей: implementation-defined, но **детерминированный** для снимка ФС (в тестах зафиксировать, напр. лексикографически по имени).

## 3. Вычисляемые свойства

### 3.1 Доступ

Синтаксис: `range.prop`. **Вызовы методов** (`range.m(...)`) в v1.1 **вне scope** — отвергать (parse или semantic error).

### 3.2 Demand-driven

Свойство считается при **первом чтении** в выражении. Результат **можно** кэшировать на значении до конца запроса.

Отдельной фазы VM «до/после хеша» нет. Порядок работы следует из того, **какие свойства форсируют выражения**:

```text
from file f in '/home/user/file'
where f.size > 0
select f.md5;
```

В `where` читается `size`; `md5` — в терминальном `select`.

```text
from file f in '/home/user/file'
where f.md5 == 'D41D8CD98F00B204E9800998ECF8427E'
select f.size;
```

`md5` форсируется в `where`.

### 3.3 Каталог свойств (v1.1)

| Приёмник | Свойство | Результат | Заметки |
|----------|----------|-----------|---------|
| `File` | `size` | `Int` | Размер в байтах |
| `File` | `<hash>` | `String` | Hex digest содержимого; имя алгоритма из `hc` |
| `String` | `size` | `Int` | Длина в байтах |
| `String` | `<hash>` | `String` | Hex digest байтов строки |
| `Hash` | `<hash>` | `String` | Путь **restore** (как legacy `from hash … select x.md5`), не «хеш от hex-символов» |
| `Dir` | *(в v1.1 нет)* | — | Файлы через `from file f in d` |
| `Record` | имя поля | значение | Поля из `{…}`, `let`, join |
| `Int` / `Bool` / `Seq` | — | — | Нет свойств в v1.1 |

Неизвестное свойство для вида → ошибка (лучше статическая, если тип range известен).

### 3.4 `from hash` + select (restore)

```text
from hash x in 'D41D8CD98F00B204E9800998ECF8427E'
select x.md5;
```

Restore / reverse алгоритмом `md5` (runners в `modes`), **не** md5 от строки digest.

## 4. Структура запроса

Синтаксис — существующая грамматика (`from` … body … `;`), не SQL-порядок.

```text
from_clause
query_body_clauses*     -- where | let | join | orderby | доп. from | …
select_or_group_clause
query_continuation?     -- into identifier query_body
```

Несколько запросов в translation unit; комментарии `#…` игнорируются.

## 5. Выражения

### 5.1 Формы (v1.1)

- Литералы string / integer  
- Идентификатор range  
- `id.prop`  
- Relational: `==`, `!=`, `>`, `>=`, `<`, `<=`, `~`, `!~`  
- Boolean: `&&`, `||`, `!`, скобки  
- `{ e1, e2, … }` и `{ name = e, … }` → `Record` (§5.3)
- Вложенный query как **значение** в `let`, `select` и полях анонимного record
- Вложенный query в **`where`** и **`orderby`**:
  - как предикат: непустая последовательность → true (**exists**)
  - как операнд сравнения / ключ сортировки: **singleton unwrap**. Именованные `Seq` (например `g.items`) **не** разворачиваются.
- Вложенный query в источниках **`from … in …` / `join … in …`**: результат — `Seq` с элементом нужного kind (или scalar payload для singleton-источника).
- Вложенный query в **ключах join** (`on … equals …`): тот же **singleton unwrap**, что и у сравнений.
- Вложенный query в ключе **`group … by`**: тот же **singleton unwrap**; в `g.key` — развёрнутый скаляр.

У nested query в value-позициях **нет собственного `into`**: `into` после вложенного `select`/`group` относится к **внешнему** запросу. На верхнем уровне `into` по-прежнему работает.

### 5.2 Равенство и нормализация ключей join

- `Int` / `Bool`: точное равенство.  
- Строки-**hex digest** из **результатов hash-свойств** (и сравнения с литералами digest): **case-insensitive**, если хотя бы один операнд — digest-значение.  
- Прочие строки (в т.ч. похожие на hex): точное равенство.  
- Смешение видов в `==`: в v1.1 — ошибка.

`~` / `!~`: левый операнд как строка; правый — pattern (`matchRe`).

### 5.3 Имена полей анонимного объекта

| Синтаксис поля | Результат |
|----------------|-----------|
| `name = expr` | Явное имя поля `name` |
| `id.prop` | Авто-имя `prop` |
| голый `id` | Авто-имя `id` |

Любое другое выражение без имени — ошибка статической проверки.

Дубликаты имён в одном record (явные alias или auto-names) — ошибка статической проверки.

## 6. Семантика выражений запроса

### 6.1 `from`

§2.3–2.4.

### 6.2 `let id = expr`

Для каждого `Env`: вычислить `expr`, выдать `Env ∪ { id ↦ value }` (с возможным shadowing).

### 6.3 `where pred`

Оставить env, где `pred` истинно.

### 6.4 `join`

**Inner equijoin** (без `into`): для каждой пары outer/inner при равенстве ключей (с нормализацией) — объединение env.

**Group join** (`join … into g`): для каждого outer — `g` = последовательность совпавших inner (возможно пустая); дальше часто `from z in g`.

### 6.5 `orderby`

Материализация + стабильная сортировка; default — ascending.

Ключи должны быть сравнимы в v1.1 (`Int`, `String`, `Bool`); неподдерживаемые формы отклоняются при статической проверке, если тип известен. Если на runtime встречаются несравнимые значения, `orderby` завершается с `TypeMismatch`.

### 6.6 `group expr by key`

Группировка текущей последовательности по `key`. Каждый элемент группы — **`Record`** с полями:

- `key` — значение ключа  
- `items` — `Seq` сгруппированных элементов

Должен поддерживаться `into` и последующий `select`.

Ключ группировки в v1.1 должен быть сравнимым (`Int`, `String`, `Bool`); при известном типе — ошибка статической проверки, иначе при несовместимых значениях — `TypeMismatch` в runtime.

### 6.7 `select expr`

| Контекст | Эффект |
|----------|--------|
| Последняя операция запроса (нет `into`) | **Sink**: печать (§7) |
| Далее `into id` | Без печати; seq → продолжение с `id` |

### 6.8 `into id`

Проекция становится `Seq`, `id` определяется в scope (legacy-баг удаления имени на `INTO` недопустим).

---

## 7. Терминальный вывод

- Один скаляр / одно свойство → одна строка на элемент.  
- Анонимный объект с несколькими полями → **по одной строке на поле** (два поля ⇒ две строки на элемент).  
- Предложение по формату: **только значения**, без имён полей (закрепить golden-тестами).

---

## 8. Ошибки

Синтаксис · семантика (undefined id, плохой prop, методы) · runtime (I/O, hash, regex). Предпочтителен fail-fast на запрос.

---

## 9. Non-goals (v1.1)

Методы · совместимость с triple-IR · встроенная рекурсия dir · микрооптимизации интерпретатора · bytecode VM.

## 10. Примеры

См. английскую версию §10 и:

```text
from dir d in '/tmp'
from file f in d
where f.size > 1000
select f.sha1;
```

```text
from file f in 'x'
select f.md5 into h
select h;
```

## 11. Архитектура реализации

Пайплайн:

```text
текст
  → parse (flex/bison) → AST
  → статическая проверка (`lower.zig`) → QueryPlan
  → interpret (`interpret.zig`)
       ↳ eval Expr в Env (demand-driven props)
       ↳ terminal select/group → sink; `into` → продолжение
```

Runtime — **tree-walk** по `QueryPlan` / `Expr` (не register/bytecode VM). Nested query values компилируются и выполняются рекурсивно и дают `Seq(Value)`.

| Выражение | Форма в `plan.zig` |
|-----------|---------------------|
| `from T x in E` | `From` / `Clause.from`, `source=.expr` |
| `from file f in d` (`d`: Dir) | `From` + `files_in_dir` |
| `let` / `where` | `Clause.let` / `Clause.where` |
| `join` / `join … into g` | `Join` (`group_into`) |
| `orderby` | `Clause.order_by` |
| `group … by` | `Clause.group_by` → Record `{ key, items }` |
| `select` / `select … into` | `Select` sink vs continuation |

Глобальной ленты `sources` нет.

| Область | Статус |
|---------|--------|
| Модули IR | `plan.zig`, `expr.zig`, `value.zig`, `interpret.zig` |
| Статическая проверка / IR | `lower.zig` |
| Выражения LINQ | полный набор v1.1 |
| Value-language | nested в value/where/orderby/from·join sources/join keys; alias `{ name = expr }` |
| Статика | свойства, join/group keys, records, часть sources |
| Диагностики | `fehler` через `diag.zig` (parse + span из AST/`Expr`) |
| Тесты | `frontend_test`, `lower_test`, `interpret`; `zig build test-l2h` |
| Методы | **Вне scope** v1.1 — parse; статическая проверка → `UnsupportedMethodCall` |
| Рекурсивный обход dir | **Вне scope** v1.1 — только плоский listing (§2.4) |

**Известные ограничения** (приняты в замороженной v1.1): часть mixed/`unknown` seq и ошибки I/O ловятся только в runtime.

Отклонено для текущего стека: packed bytecode / register VM; сохранение triples; SQL cost-based optimizer.

## 12. Закрытые решения (бывшие открытые вопросы)

| Тема | Решение |
|------|---------|
| Авто-имена Record | `id.prop` → поле `prop`; голый `id` → `id`; иное выражение в `{…}` → **ошибка** (§5.3) |
| `from file f in d` | Только **`Dir`** |
| Symlink при listing | **Пропускать** все symlink |
| Hex | **Печать lowercase**; сравнение case-insensitive |
| Элемент `group … by` | Record `{ key, items }`, `items` — последовательность |

Открытых вопросов нет. Дальнейшие семантические изменения — по правилам правок в шапке документа.
